## Overview

PikaOS uses a modern bootloader and initramfs setup that differs significantly from stock Debian. This document explains what changed, why it was done, and how it works internally.

---

## Key Changes from Debian

### 1 Bootloader: rEFInd Instead of GRUB

**Debian:** uses `GRUB` (Grand Unified Bootloader)
**PikaOS:** uses `rEFInd` (`EFI`-based boot manager)

### Why the Change?

- **Simplicity:** `rEFInd` is easier to configure and less prone to menu corruption
- **Automatic detection:** Finds all installed kernels and `initrds` automatically
- **Better graphics:** Modern `EFI` stub support with clean graphics output
- **Secure Boot ready:** Works seamlessly with shim bootloader for Secure Boot support

### How It Works

When you boot, `rEFInd` scans your system for:
- Linux kernels (in `/boot` or `EFI` partition)
- `initramfs` images (generated by `booster`)
- Windows Boot Manager (for dual-boot systems)

It presents all options in a menu with icons and descriptions.

---

### 2 Initramfs Generation: booster Instead of mkinitramfs

**Debian:** uses `mkinitramfs` to create `initramfs` images
**PikaOS:** uses `booster` (a faster, more flexible alternative)

### What is initramfs?

The initial RAM filesystem (initramfs) is a temporary root filesystem loaded into memory before the real root filesystem is mounted. It contains:
- kernel modules for your hardware drivers
- scripts to mount your root partition
- tools needed to transition from ramfs to the real root

### Why Change mkinitramfs to booster?

- **Faster generation:** `booster` uses Go, which compiles init images much faster
- **Better integration:** Works seamlessly with rEFInd and Secure Boot
- **Modular design:** Easier to customize for different use cases
- **Active maintenance:** PikaOS maintains `booster` patches for optimal performance

---

### 3 Secure Boot Integration via Shim

PikaOS uses a chain of trust approach for Secure Boot:

### The Chain

1. **Shim bootloader** (Microsoft signed)
   - Loads when your PC boots with Secure Boot enabled
   - Verifies its own signature against trusted Microsoft keys
   - Then loads `rEFInd`

2. **rEFInd stub**
   - Loaded by shim after it verifies itself
   - Presents the boot menu

3. **Signed kernel and initramfs**
   - Both signed with PikaOS's MOK (Machine Owner Key)
   - Enrolled once via the bluescreen MOK management prompt
   - After enrollment, updates handle signing automatically

### How It Works

```
Boot sequence with Secure Boot:
┌─────────┐    ┌──────────────┐    ┌──────────┐    ┌─────────┐
│BIOS/UEFI│───▶│   Shim       │───▶│ rEFInd   │───▶│ Kernel  │
└─────────┘    └──────────────┘    └──────────┘    └─────────┘
                    (Microsoft signed)                (PikaOS signed)
```

## Technical Details

### EFI System Partition Structure

The `/boot/efi` partition typically contains:

```
/boot/efi/
├── BOOT/              # Microsoft fallback folder
│   └── bootx64.efi    # Shim bootloader (default entry)
├── refind/            # rEFInd in standard mode
│   ├── refind_x64.efi
│   └── drivers_x64/
└── BOOT.refind/       # Alternative fallback for shim
    └── refind_x64.efi
```

When Secure Boot is enabled:
- BIOS loads BOOT/bootx64.efi (shim)
- Shim verifies and loads the PikaOS-signed rEFInd
- rEFInd presents boot menu

---

### Booster Initramfs Contents

The booster-generated initramfs includes:

- Hardware detection scripts
- NVIDIA/Mesa/AMD driver modules (depending on your system)
- Root filesystem mounting logic
- PikaOS-specific initialization scripts
- Secure Boot verification if enabled

## Troubleshooting

### rEFInd not appearing with Secure Boot

If you see "No bootable option found" with Secure Boot enabled:

1. Check that MOK is enrolled: `mokutil --sb-state`
2. If not, re-run `sudo pika-secureboot enable` and complete the enrollment
3. Reboot and verify shim loads correctly

### Wrong kernel selected at boot

rEFInd should auto-detect kernels. If it's picking the wrong one:

1. Check `/boot/EFI/refind/settings.ini` for configuration options
2. Verify kernel versions with `uname -r`
3. Consider regenerating initramfs if modules don't match

### Initramfs mounting issues

If your root partition won't mount after reboot:

1. Check boot logs with `journalctl -xb -p 3`
2. Verify filesystem type matches what's expected
3. Rebuild initramfs: `sudo booster-kernup --all`
